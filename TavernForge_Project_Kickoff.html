Product mission

TavernForge is a FOSS Android companion for assembling, authoring, validating, organizing and exporting SillyTavern character cards and World Info/lorebooks. It supports imported assets, manual creation and Gemini-assisted creation without requiring an account or backend.

Non-negotiable principles

Format fidelity · strict validation · no hardcoded credentials · explicit AI consent · transparent API usage · local ownership · lossless preservation of unknown fields.

02 · Three primary workflows

01

Combine existing files

Import-firstNo AI required

For users who already have character JSON, lorebook JSON and/or character artwork.

SELECT → INSPECT → ASSOCIATE → VALIDATE → EXPORT
  • Import character card JSON.
  • Import standalone lorebook JSON.
  • Import PNG and inspect embedded SillyTavern metadata.
  • Associate the lorebook and artwork with the character.
  • Resolve validation errors or review warnings.
  • Export supported JSON and/or PNG output.
Partial inputs are valid: a user may start with only JSON, only a PNG card, or a character plus a separate lorebook. The app must clearly show what is missing and what can be exported.
02

Generate with Gemini

AI-assistedBYOK

For users who provide a Gemini API key and want models to create the required structured content from a concept.

CONFIGURE → CONCEPT → GENERATE → VALIDATE → REVIEW → EXPORT
  • Add and verify the user's own API key.
  • Select an available, compatible Gemini model.
  • Describe the character, setting and intended tone.
  • Generate character card JSON and lorebook JSON.
  • Optionally request image generation if explicitly enabled and supported by the selected model.
  • Validate, review and accept generated content before saving.
Text generation and image generation are separate permissions. Image generation must be disabled by default and must never be inferred from permission to generate text.
03

Build manually

Form-firstNo API key

For users who want complete control or do not want to use AI.

CHOOSE TEMPLATE → FILL DETAILS → AUTHOR LORE → VALIDATE → EXPORT
  • Guided character form with required and optional fields.
  • Basic and advanced authoring modes.
  • Manual lorebook and entry creation.
  • Optional artwork attachment.
  • Live validation and completeness indicators.
  • Export without any network access.
The form must explain fields and distinguish specification-required fields from recommended authoring fields. Do not label optional creative fields as format-required.

Shared project model

All three workflows must converge on one canonical internal project representation. Do not build three independent storage or export systems. Import, AI generation and manual forms should all produce/update the same domain model, then pass through the same SillyTavern format engine and validation pipeline.

03 · Functional requirements

Character card authoring

  • Name, creator, character version, tags and creator notes.
  • Description, personality, scenario and relevant prompt fields.
  • First message, alternate greetings and example dialogue.
  • Speech style, vocabulary, mannerisms and communication guidance.
  • Appearance, clothing/attire and visual description as authoring fields.
  • Advanced specification fields, extensions and metadata.
  • Basic mode and advanced mode.

The UI may offer convenient authoring fields that are not standard top-level fields in every card version. The format adapter must map them only where the target format supports them, or preserve them as explicitly documented app metadata without pretending they are native fields.

Lorebook / World Info editor

  • Create, import, edit, duplicate, reorder and delete entries.
  • Primary keys, secondary keys and selective logic.
  • Constant activation, case sensitivity and matching options.
  • Insertion order, position, depth and probability where supported.
  • Entry comments, content and enabled/disabled state.
  • World-level settings and character associations.
  • Standalone lorebook import/export.

PNG and asset handling

  • Read supported embedded SillyTavern metadata from PNG.
  • Display extracted metadata and validation results before import.
  • Preserve image bytes where possible when editing metadata.
  • Export PNG with the correct metadata chunk for the selected card format.
  • Support JSON-only export when no image exists.
  • Store large image files in app-private files; keep references and metadata in the database.
  • Handle corrupt, unsupported and metadata-free PNGs without crashing.

Project library

  • Local character and lorebook library.
  • Search, sort, filter, tag and duplicate.
  • Recent projects and draft states.
  • Link one lorebook to multiple characters where the format and product model allow.
  • Backup/export project data.
  • Delete and restore safeguards where practical.

04 · SillyTavern format engine & strict validation

Critical subsystem
Hard requirement: All supported character-card, PNG metadata and lorebook formats must be implemented from the SillyTavern format engine/specifications. Do not invent a TavernForge-native replacement format and do not treat a loosely similar JSON shape as compatible.

Format-engine policy

  • Maintain explicit adapters/parsers/serializers for each supported SillyTavern format version.
  • Keep format version information attached to imported projects.
  • Validate against the exact target version's required structure and semantics.
  • Do not silently upgrade, downgrade, normalize away or discard fields.
  • Preserve unknown fields and extension data through round trips whenever possible.
  • Separate parsing, semantic validation, migration and serialization.
  • Keep format-engine code independent of Compose and UI models.
  • Track upstream format changes and add compatibility fixtures before claiming support.

Character-card formats

Target the SillyTavern-supported character-card versions that are confirmed by the upstream specification and fixtures. Initial scope: V1 import where feasible, V2 and V3 support according to verified upstream definitions.

Do not advertise a version as fully supported until import, edit, round-trip and export tests pass against real upstream fixtures.

PNG metadata

Implement the actual metadata chunk conventions used by SillyTavern for each supported card version (including the relevant chara and ccv3 paths where applicable). Validate chunk presence, encoding, payload and decoded card structure.

Do not simply append JSON bytes to an image or rename a file extension.

Lorebook / World Info

Follow SillyTavern World Info semantics and actual field names, defaults and value types. Cover entry keys, secondary keys, selective matching, activation, insertion, probability, recursion and world-level configuration as supported by the upstream version.

Validation levels

  • Parse: valid JSON/PNG structure and decoding.
  • Schema: required fields, types, enums and version rules.
  • Semantic: field relationships and supported value constraints.
  • Compatibility: target SillyTavern version/format behavior.
  • Round-trip: import → edit/no-op → export preserves meaningful data.

Validation behavior

SeverityMeaningExport policy
ErrorInvalid structure, missing required data, wrong type, malformed metadata or incompatible value.Block strict export until fixed, unless an explicit safe export mode is defined for that format.
WarningPotentially lossy conversion, unknown extension, unsupported optional feature or suspicious but parseable data.Require user review/acknowledgement for risky transformations.
InfoNon-blocking suggestion, completeness or quality recommendation.Allow export.
Lossless round-trip requirement: For imported data, unknown fields must be retained in a raw/extension representation and emitted again unless the user explicitly removes them or a documented format conversion makes preservation impossible. If preservation is impossible, disclose exactly what will be lost before export.

Source-of-truth references to pin and review during implementation: SillyTavern documentation and upstream source/schema/fixtures. The project must record the upstream repository URL, commit/tag or documentation revision used for each implemented format adapter. Do not rely on memory or third-party summaries as the format contract.

05 · Gemini integration & transparent API usage

Bring Your Own Key (BYOK)

  • User supplies their own Google AI Studio API key.
  • No API keys, tokens or credentials may be hardcoded in source, resources, build files, tests, sample configs or repository history.
  • Never ship a shared developer key or proxy requests through a hidden backend.
  • Store the key locally using Android Keystore-backed encryption; never store it as plaintext in ordinary DataStore preferences.
  • Mask the key in UI, exclude it from logs, crash reports, analytics and exported project files.
  • Provide explicit update, verify and delete-key actions.
  • Explain that Google may bill or apply quotas according to the user's Google AI Studio/API account terms.

API Usage & Permissions panel

The settings screen must expose a clear, user-controlled panel that explains exactly what the key may be used for. No permission is implied by another permission.

PermissionDefaultBehavior
Use Gemini for text generationOff until enabledAllows requests for character JSON, lorebook JSON, field writing, expansion and review.
Use Gemini for image generationOffAllows image-generation requests only when the selected model/API supports image output. Must require a separate opt-in.
Allow automatic follow-up requestsOffAllows multi-step generation workflows to make additional calls. Otherwise, ask before follow-up calls.
Image generation is a separate capability and permission. If disabled, the app must not send image-generation prompts or invoke an image-capable model for image output. If the selected model does not support image generation, show that capability as unavailable rather than silently substituting another model.

Usage transparency for every request

Before execution, show a request preview with:

  • Provider and exact selected model ID.
  • Request purpose: character, lorebook, field rewrite, image, etc.
  • What user content will be sent (concept, selected character fields, lore entries, image prompt or reference).
  • Whether image generation is involved.
  • Configured generation limits and any available token/cost estimate, clearly labelled as estimate.
  • Whether the request is one call or a multi-step workflow.

After execution, show returned usage metadata when the provider supplies it (for example input/output token counts). Never invent exact costs where the provider does not return enough data. Link the user to the provider's current pricing/quota information.

Generation capabilities

  • Generate complete character-card content from a bare concept.
  • Generate lorebooks and lore entries.
  • Generate character-aware lore from an existing project.
  • Rewrite or expand selected fields.
  • Generate alternate greetings and example dialogue.
  • Generate artwork only with image permission and compatible model.
  • Validate generated output before it enters the saved project.

Safe generation pipeline

  1. Check permission and key availability.
  2. Resolve selected model capability.
  3. Show request preview and obtain confirmation as configured.
  4. Build prompt using versioned prompt templates.
  5. Call provider through Ktor client.
  6. Parse structured output; never trust raw model output.
  7. Run strict SillyTavern validation.
  8. Present diff/review and accept/reject actions.
  9. Save only after explicit user acceptance.
Generation is not authority: Gemini output is untrusted draft content. It must never bypass the format engine, validation, user review or explicit save/replace confirmation.

06 · Architecture & data ownership

Architecture principles

  • Offline-first, local-first and account-free.
  • MVVM with unidirectional data flow.
  • Separate data, domain and presentation layers.
  • Repositories own persistence and data-source coordination.
  • Room is the source of truth for saved structured projects.
  • DataStore holds non-secret user preferences.
  • Keystore-backed encrypted storage holds API credentials.
  • Ktor is isolated behind provider/network interfaces.
  • Format engine is pure/domain-oriented and independent of UI.
  • All file access uses scoped storage/document picker and app-private managed assets as appropriate.

08 · Multi-agent team & execution protocol

Agent 0 · Supervisor

  • Owns project execution and final decisions.
  • Delegates, integrates and resolves conflicts.
  • Maintains source-of-truth documents and status.
  • Builds the UI comparison HTML from Agent 3 proposals.
  • Obtains user approval before UI direction is locked.
  • Reviews release readiness.

Agent 1 · Scope & dependency planner

  • Requirements decomposition and acceptance criteria.
  • Module boundaries, interfaces and data contracts.
  • Dependency/version compatibility matrix.
  • Risk analysis, task graph and sequencing.
  • Upstream SillyTavern format research and fixtures plan.

Agent 2 · Functionality implementor

  • Build configuration and core foundations.
  • Room3, repositories and domain logic.
  • Format engine, import/export and validation.
  • Gemini client, key security and usage controls.
  • Implements approved UI and integrations.

Agent 3 · UI/UX expert

  • Proposes materially different UX directions.
  • Information architecture and navigation.
  • Wireframes, prototypes and component system.
  • Responsive/adaptive layouts and accessibility.
  • Documents trade-offs and rationale.

Agent 4 · Tester

  • Unit, integration and UI tests.
  • Format fixtures, PNG and round-trip tests.
  • Gemini mocks, permission and failure-path tests.
  • Regression and build compatibility checks.
  • Reports reproducible defects and evidence.

Execution order — parallel work with a mandatory design gate

  1. Agent 0 kickoff: establish goals, constraints, repo rules and assignments.
  2. Parallel discovery: Agent 1 defines scope/contracts/dependencies; Agent 3 explores UX directions; Agent 2 may build only agreed non-UI foundations; Agent 4 prepares test strategy and fixtures.
  3. Agent 0 integration: review proposals and create the comparison page from Agent 3's actual work.
  4. Mandatory user decision: user selects one approach or requests a hybrid. No final UI implementation before approval.
  5. Implementation: Agent 2 builds to approved contracts and design; Agent 1 tracks scope; Agent 3 supports design QA; Agent 4 tests incrementally.
  6. Release review: Agent 4 provides test evidence; Agent 0 checks acceptance criteria and unresolved risks.
UI comparison HTML deliverable: at least three distinct proposals — (A) Material Expressive Native, (B) Studio Workspace/editor-first, (C) Hybrid Tavern/character-library-first. Include comparable screen previews, navigation, key workflows, component treatments, strengths, weaknesses, accessibility/adaptive considerations and a recommendation. The page must let the user clearly choose A/B/C or request a hybrid. The selection is a decision gate, not an automatic implementation trigger.

Agent operating rules

  • Agents must read the current project documents before changing architecture or contracts.
  • One owner per file/module at a time; coordinate shared-file changes.
  • Do not fabricate API behavior, format fields, dependency compatibility or test results.
  • Every task has scope, inputs, output artifacts and acceptance criteria.
  • Agents report blockers and assumptions explicitly.
  • No secrets in prompts, logs, commits, test fixtures or generated documentation.
  • Agent 0 is responsible for reconciling contradictory recommendations rather than silently merging them.

Definition of success

A user can choose any of the three workflows — combine existing assets, generate with their own Gemini key, or create manually — and end with a strictly validated SillyTavern-compatible character card and lorebook. They retain control over API usage, especially image generation. Their projects remain local, their credentials remain private, and importing/editing/exporting does not silently destroy data.

TavernForge should be a reliable format tool first, a great authoring experience second, and an AI assistant third. AI is optional; format correctness is not.
